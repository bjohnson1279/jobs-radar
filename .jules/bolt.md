## 2026-05-26 - Eliminate remaining structuredClone on mutation paths in store
**Learning:** While `store.snapshot()` previously transitioned from `structuredClone(state)` to shallow cloning (`createSnapshot`), `store.mutate()` was still calling `structuredClone(state)` on every mutation (e.g. `setApplied` and `recordSearch`). In stores containing thousands of job postings, `structuredClone` incurs recursive graph traversal, deep string cloning, and GC pressure (~3,127ms for 1,000 clones of 1,000 jobs). Reusing `createSnapshot(state)` within `mutate` provides identical state isolation and immutability before persistence in ~85ms (~36x speedup).
**Action:** When optimizing snapshot cloning for large collections, verify that internal mutation and rollback queues also reuse the fast shallow clone helper instead of leaving `structuredClone` on mutation hot paths.

## 2026-05-26 - In-memory caching of static web assets in local Node server
**Learning:** `server.ts` handles root and asset requests (`/`, `/app.js`, `/style.css`) by performing an asynchronous disk read (`readFile`) on every incoming request. Even on local SSDs, repeated disk reads and filesystem syscalls add significant overhead (~2,231ms per 2,000 requests, ~1.12ms/req). Caching the read static asset Buffers in an in-memory `Map` on first read reduces serving latency to ~669ms per 2,000 requests (~0.33ms/req, ~3.3x speedup, ~70% lower latency) and completely eliminates redundant filesystem I/O for web UI client sessions.
**Action:** In lightweight Node HTTP servers serving static frontend assets, cache loaded asset file buffers in an in-memory Map after the first read instead of issuing disk `readFile` syscalls on every asset request.

## 2026-05-25 - Short-circuiting and cheap-field filtering in client-side search
**Learning:** `web/app.js` runs `render()` on initial load, data refresh, filter dropdown changes, and every input keystroke. Previously, it constructed a full template string `${job.company} ${job.title} ${job.description}` and lowercased it for every job in memory before evaluating application and location filters. For feeds with hundreds or thousands of listings with long descriptions, this generated substantial GC pressure and took ~641ms per 100 empty-query render cycles. Evaluating cheap boolean flags (application and location filter dropdowns) first, skipping string checks entirely when the search query is blank (~70x speedup, ~9.3ms per 100 runs), and short-circuiting on `company` and `title` before scanning `description` reduces latency by ~50% even on active searches without template string allocations.
**Action:** In client-side list filtering, evaluate cheap scalar and status filters before text matching, avoid concatenating large strings when testing multi-field queries, and short-circuit early on empty query terms.

## 2026-05-24 - Integer calendar validation and bounded caching for date parsing
**Learning:** `sourceDate` is called on all incoming listing dates across Greenhouse, Lever, Ashby, RemoteOK, Jobicy, and application updates. Previously, it validated dates by template-string formatting, parsing `Date.parse(\`${calendar}T00:00:00Z\`)`, and instantiating `new Date(...).toISOString()`. This double date object construction, string concatenation, and ISO string generation took ~3,240ms for 1.6M invocations. Using fast integer calendar validation (checking month boundaries and leap year days) reduces execution time to ~1,300ms (~2.5x speedup), and adding a bounded Map cache (capped at 1,000 entries) for repeated feed dates brings runtime down to ~106ms (~30x speedup) with minimal memory footprint.
**Action:** Validate calendar date components using direct integer ranges and leap-year arithmetic rather than allocating round-trip Date objects, and cache date parsing results for feed ingest paths where dates repeat frequently.

## 2026-05-23 - Targeted shallow object cloning over structuredClone for store snapshots
**Learning:** `store.snapshot()` was executing `structuredClone(state)` on every API read request (`/api/jobs`) and validation check. For stores holding thousands of job listings with long text descriptions, `structuredClone` incurs massive serialization and graph traversal overhead (~5,292ms for 1,000 snapshots of 2,000 jobs). Because tracked job records are shallow objects with only optional shallow salary metadata, creating a new snapshot object via array `.map()` and object spread `{ ...job }` provides full data immutability in ~110ms (~48x speedup) with significantly less GC churn.
**Action:** Prefer explicit shallow spread cloning over `structuredClone` when taking read snapshots of large collections with known shallow schemas to avoid costly deep graph traversal overhead.

## 2026-05-22 - Pre-sort static tier structures and eliminate per-call array and closure allocations
**Learning:** `locationTierLabel` was executing `[...settings.location.tiers].sort((a, b) => b.points - a.points).find(...)` on every formatted job card. Sorting a newly cloned array and allocating a predicate closure on each invocation incurred ~900ms per 1M calls. Pre-sorting the static configuration array once at module load time and doing a direct `for ... of` scan reduces runtime to ~28ms (~31x speedup) with zero heap garbage generated per call.
**Action:** Pre-sort static configuration arrays once at module scope and use straightforward loops instead of re-cloning, re-sorting, and allocating closures in formatting and presentation hot paths.

## 2026-05-21 - Early location eligibility filter before full-text scoring
**Learning:** `rankJobs` previously evaluated `plainText(job.description)` and executed all multi-regex scoring rules (`scoreJobDetails`) across thousands of jobs before discarding non-matching locations in a subsequent `.filter()`. Because `parseLocation` is memoized and fast, filtering location eligibility immediately after location resolution avoids expensive text manipulation and scoring allocations on candidate listings that are immediately dropped. In addition, replacing chained `.filter().map().filter()` with a single push loop eliminates intermediate array allocations, yielding an overall ~1.46x speedup (~31% lower ranking latency).
**Action:** In search and ranking pipelines, filter candidates on cheap/cached attributes (e.g. location, title, blocklists) before triggering expensive full-text cleaning and rule evaluations.

## 2025-05-20 - Fast-path scoring and title/company memoization
**Learning:** In list pipeline scoring, creating `new Set()` objects on every item for rule group deduplication and constructing unused `reasons`/`pros`/`cons` arrays during raw scraping calls adds significant GC and string formatting overhead. Parametrizing detail construction and using lazy array checks for small group sets, alongside Map memoization for company normalization and title filters, yields a ~30% performance boost for job scoring and ranking.
**Action:** Avoid allocating intermediate reporting structures (reasons, pros, cons) in high-throughput pipeline scoring methods when only numerical metrics are required, and lazy-initialize group collections.

## 2025-05-20 - Reuse precomputed scoring reasons and guard salary regex in presentation output
**Learning:** `formatJob` was re-invoking `scoreJobDetails` from scratch over thousands of long job descriptions, executing 25+ regular expressions per job a second time. Additionally, scanning unconstrained job descriptions with a salary regex incurred unnecessary evaluation when no `$` was present. Reusing `j.reasons` with fallback to `scoreJobDetails` and pre-checking `description.includes('$')` provides a ~33x speedup on formatting batches.
**Action:** Always forward and reuse calculated domain scoring/breakdown metadata into presentation formatters rather than re-evaluating rule engines, and guard salary regex passes with cheap substring pre-checks.

## 2025-05-18 - Fast-path check and single-pass cleaning in V8 text processing
**Learning:** In V8, string replacement callbacks `replace(regex, fn)` incur JS-to-C++ boundary overhead when processing large HTML descriptions. Chained regexes remain faster, but fast-path checking (`includes('<') || includes('&')`) before executing multi-pass entity regexes completely skips redundant scans on clean strings. **Action:** Always clean strings once at the entry point of pipeline transformations, and add cheap substring pre-checks (`includes`) before running multi-regex string replacement sequences.
